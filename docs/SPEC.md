# 1. プロジェクト概要

## 1.1 目的

東京都および埼玉県の立ち呑み屋を3D地図上に表示し、店舗検索、価格・ジャンルの比較、酒場密度の可視化、はしご酒の計画、訪問記録、街の歴史の探索を一体化したアプリケーションを開発する。

一般的な飲食店検索サービスの代替を目指すのではなく、立ち呑み文化を楽しみながら、実際の飲み歩きに役立ち、自分自身の酒場遍歴が蓄積されるツールを目指す。

## 1.2 基本コンセプト

本アプリは、以下の4つの価値を提供する。

1. 実用性：条件に合う店を探し、営業情報や予算を確認できる。
2. 文化：街ごとの酒場密度、ジャンル、価格帯、歴史的変化を比較できる。
3. 探検：未訪問の駅や街を発見し、はしご酒ルートを計画できる。
4. 個人記録：訪問した店、注文した料理、感想、写真、発見を蓄積できる。

## 1.3 設計原則

- 3D地図をアプリの中心に置く。
- 地図を眺めるだけでも発見があるようにする。
- 店舗の事実情報と個人的な感想を分離する。
- 情報の出典と最終確認日を管理する。
- 未確認情報を確認済み情報として表示しない。
- 初期段階では個人利用に特化し、認証・SNS・公開口コミ機能は実装しない。
- サーバー運用を必要としない構成から開始する。
- 将来のデータベース移行や機能追加を妨げない設計とする。
- データが少ない地域を、酒場が少ない地域と誤認させない。
- 実在店舗の情報、営業時間、価格、営業状況を捏造しない。

## 3.1 基本技術

以下を初期候補とする。開発開始時に現在の公式ドキュメントと依存関係を確認し、互換性のある安定版を採用すること。

- 言語：TypeScript
- UI：React

- 地図データ：OpenStreetMap等の利用条件を満たすデータソース
- 個人データ保存：IndexedDB

既存リポジトリに開発環境がある場合は、最初に構成を調査する。既存の設計や依存関係を理由なく全面変更しない。

## 3.2 アーキテクチャ

アプリを以下の層に分ける。

1. UI層：地図、パネル、検索、フォーム、一覧
2. 地図層：MapLibreの初期化、マーカー、密度表示、地図イベント

5. 外部データ層：地図タイル、外部経路サービス、任意のデータ取得処理

UIコンポーネントからIndexedDBやMapLibreの内部APIを直接乱用しない。各層の責務を分け、テスト可能な構造とする。

# 4. 画面仕様

## 4.1 メイン画面

メイン画面は3D地図を最大限広く表示する。

画面構成：

- 上部：アプリ名、検索欄、地域切り替え、設定
- 左側：検索条件と表示レイヤー
- 中央：3D地図
- 右側：選択した店舗の詳細パネル
- 下部：選択中のレイヤーに応じた凡例または操作情報

詳細パネルは閉じられるようにし、地図を広く見たいときには非表示にできるようにする。

地図の上に大量の固定パネルを重ねない。検索結果の件数、選択店舗、現在のフィルター条件を確認できること。

## 4.2 地図操作

次の操作を提供する。

- ズームイン・ズームアウト
- ドラッグによる地図移動
- 回転・傾きの操作
- 初期表示範囲への復帰
- 東京都・埼玉県を含む広域への移動
- 選択店舗への移動
- 店舗マーカーの選択
- 密集時のマーカーのクラスタリング
- レイヤー切り替え

地図の初期表示位置は東京都と埼玉県を探索しやすい範囲とする。正確な中心座標は実装時に設定し、画面サイズや地図スタイルに応じて調整する。

地図を操作している間、不要な再描画やデータの再取得を繰り返さない。

## 4.3 店舗詳細パネル

表示項目：

- 店名
- 店舗の座標・住所
- 立ち呑み形式
- 料理ジャンル
- 酒の種類
- 価格例
- 予算帯
- 営業時間
- 営業情報の確認状況
- 最終確認日
- 情報の出典
- 公式サイト等へのリンク
- お気に入り登録
- 行きたい店への登録
- 訪問記録の追加
- 店舗情報の編集

不明な情報は「未確認」と表示し、勝手に補完しない。

## 4.4 検索・フィルター画面

以下の条件を組み合わせて検索できるようにする。

- 店名
- 都道府県
- 市区町村
- 最寄り駅
- 料理ジャンル
- 酒の種類
- 予算帯
- 指定予算内の注文モデル
- 立ち呑み専業か、座席併設か
- 営業時間の曜日
- 営業時間帯
- 訪問済み・未訪問
- お気に入り
- 情報の確認状況

複数条件を同時に指定できること。

条件解除ボタンを設け、現在適用中の条件を視覚的に分かるようにする。

「営業中」の表示は、確認済みの営業時間から判定できる範囲に限る。臨時休業や最新状況が未確認の場合は、その制約を明示する。

## 4.5 酒場密度レイヤー

地図上の店舗密度を、色または高さで表現する。

最低限、以下を切り替えられるようにする。

- 通常の店舗マーカー
- 店舗密度ヒートマップ
- 料理ジャンル別の分布
- 予算帯別の分布
- 訪問済み店舗の分布

地図の縮尺が広いときは集約表示し、拡大時に個別店舗が分かるようにする。

密度の集計対象は、原則として現在のフィルター条件を反映する。

凡例を表示し、色や高さが何を意味するか説明する。

データ件数が少ない地域では、密度を過大評価させない。未調査地域を「店舗が少ない」と断定する表示はしない。

# 5. 3D地図の視覚仕様

## 5.1 基本方針

街の形状を楽しみながら、店舗を探す実用性を失わないデザインとする。

推奨する初期デザイン：

- 落ち着いた濃色または中間色の地図
- 建物は周辺地図と区別できる色で表示
- 店舗マーカーは十分なコントラストを持たせる
- 選択中の店舗は明確に強調する
- 密度表示では凡例を必ず設ける
- 操作ボタンは地図の重要な領域を塞がない

派手なアニメーションよりも、読みやすさ、応答性、情報の判別性を優先する。

## 5.2 マーカー表示

店舗のジャンルを識別できるアイコンを用意する。

例：

- 焼きとん・焼き鳥
- 煮込み
- おでん
- 刺身・海鮮
- 日本酒
- ビール・ホッピー
- 角打ち
- その他・未分類

複数ジャンルを持つ店舗は複数のタグで表現できるようにする。

マーカーの色だけに情報を依存させず、詳細カードと凡例でも意味を確認できるようにする。

# 6. 店舗データモデル

## 6.1 Shop型

店舗データは以下の構造を基本とする。

```ts
type ShopStatus =
  | "unverified"
  | "verified"
  | "possibly_closed"
  | "closed";

type PriceExample = {
  itemName: string;
  priceYen: number | null;
  checkedAt: string | null;
  sourceId: string | null;
};

type OpeningHours = {
  dayOfWeek: number;
  opensAt: string | null;
  closesAt: string | null;
  isClosed: boolean | null;
  note?: string;
};

type Shop = {
  id: string;
  name: string;

  latitude: number;
  longitude: number;
  address: string | null;

  prefecture: "東京都" | "埼玉県" | null;
  municipality: string | null;
  stationIds: string[];

  categories: string[];
  drinkTags: string[];

  standingOnly: boolean | null;
  hasSeating: boolean | null;

  priceLevel: "budget" | "standard" | "premium" | "unknown";
  priceExamples: PriceExample[];

  openingHours: OpeningHours[];
  officialUrl: string | null;

  status: ShopStatus;
  sourceIds: string[];

  createdAt: string;
  updatedAt: string;
  lastVerifiedAt: string | null;

  notes?: string;
};
```

座標はWGS84の緯度・経度を使用する。緯度と経度の順番を地図ライブラリに渡す際は、そのAPIが要求する座標形式に合わせて変換する。

価格例は複数登録できるようにする。価格の確認日と出典を店舗全体の確認日とは別に管理する。

## 6.2 駅データ

```ts
type Station = {
  id: string;
  name: string;
  latitude: number;
  longitude: number;
  prefecture: string | null;
  municipality: string | null;
  lines: string[];
};
```

同名駅や複数路線の駅を区別できるように、駅名だけで識別しない。

## 6.3 情報ソース

```ts
type DataSource = {
  id: string;
  type:
    | "official_site"
    | "open_data"
    | "manual"
    | "field_check"
    | "other";

  name: string;
  url: string | null;
  accessedAt: string | null;
  notes: string | null;
};
```

各店舗の情報がどの出典に基づくのかを追跡できるようにする。

出典URLは外部リンクとして表示する。URLの存在だけで、その情報が正確であると判定してはならない。

# 7. 個人記録のデータモデル

## 7.1 訪問記録

```ts
type Visit = {
  id: string;
  shopId: string;

  visitedAt: string;
  orderedItems: string[];

  amountYen: number | null;
  rating: number | null;

  atmosphereTags: string[];
  memo: string;

  photoRefs: string[];

  createdAt: string;
  updatedAt: string;
};
```

訪問記録は店舗データから独立して管理する。

店舗の名称や住所が変更されても、過去の訪問記録が消えないようにする。

評価は1〜5など一定の範囲に制限し、未評価を許容する。感想の入力は任意とする。

## 7.2 お気に入り・行きたい店

お気に入りと行きたい店を区別する。

- お気に入り：気に入った店
- 行きたい店：今後訪問する候補
- 再訪したい店：再び行く意思がある店

これらは個人設定として保存する。店舗データ本体に個人の評価や訪問状態を混在させない。

## 7.3 ルートデータ

```ts
type PlannedRoute = {
  id: string;
  name: string;

  shopIds: string[];
  startStationId: string | null;

  budgetYen: number | null;
  plannedDurationMinutes: number | null;

  memo: string;

  createdAt: string;
  updatedAt: string;
};
```

店の順序は `shopIds` の配列順で表す。

v1.0では手動で店舗を追加し、順序を入れ替えられることを優先する。自動最適化は将来の拡張とする。

# 8. データ保存とバックアップ

## 8.1 保存方式

店舗の初期データはJSONファイルとして保持する。

ユーザーによる追加・編集・訪問記録はIndexedDBに保存する。

データアクセスはRepository層を経由し、画面コンポーネントからIndexedDBを直接操作しない。

## 8.2 データの統合

アプリ起動時には、初期店舗データとユーザーが追加・変更したデータを整合的に統合する。

店舗IDを主キーとして扱い、同じ店舗を重複登録しないようにする。

初期データを更新した際に、ユーザーの訪問記録や個人メモが消えないこと。

データの形式を変更する場合は、バージョン番号を設け、必要に応じて移行処理を実装する。

## 8.3 JSONのエクスポート・インポート

最低限、以下を実装する。

- 全店舗データのエクスポート
- 個人記録のエクスポート
- 全データのバックアップ
- バックアップJSONの読み込み
- 読み込み前の形式検証
- 不正なデータがある場合のエラー表示
- 既存データを上書きする場合の確認
- 重複IDや参照先不明の記録への対処

インポートは検証が完了してからデータを変更する。途中でエラーが起きた際に、データが半端な状態で更新されないようにする。

# 9. 予算計算

## 9.1 注文モデル

店舗に登録された価格例を利用し、注文の合計額を計算する。

例：

- 飲み物1：価格確認済みの登録価格
- 飲み物2：価格確認済みの登録価格
- つまみ1：価格確認済みの登録価格

合計額は登録済み価格の合算とする。

チャージ・お通し・税・サービス料などが不明な場合、合計額を確定金額として表示しない。

## 9.2 予算別検索

以下のような予算条件で店舗を絞り込めるようにする。

- 1,000円以内
- 2,000円以内
- 3,000円以内
- 任意の予算

注文例が登録されていない店舗については、予算内で飲めると断定しない。

# 10. はしご酒プランナー

## 10.1 v1.0の必須機能

- 店舗をルートに追加する
- 店舗の順番を入れ替える
- ルートから店舗を削除する
- ルート名を付けて保存する
- 想定予算を入力する
- 想定所要時間を入力する
- ルートに含まれる店舗を地図上で強調する
- 各店舗の住所と営業時間を確認する

## 10.2 経路表示

徒歩ルーティングAPIが利用可能な場合は、店舗間の徒歩経路と所要時間を表示する。

APIを利用できない場合は、直線距離を参考値として表示し、徒歩距離や徒歩所要時間と誤認させない。

徒歩時間を概算する場合は、概算であることを明示する。

## 10.3 時間計画

各店舗の滞在時間は利用者が設定できるようにする。

営業時間が確認済みの場合は、訪問予定時刻との比較を補助する。

営業時間が不明な店舗については、訪問可能と断定しない。

終電情報の自動取得はv1.0の必須要件としない。

# 11. 酒場文化・街の記録

v1.0では、店舗情報を地図に表示する基盤を優先する。歴史情報の大規模な収集は後回しにする。

将来拡張に備え、以下の情報を追加できる構造とする。

- 店舗の創業年
- 旧店舗名
- 建物や商店街の歴史
- 古い写真
- 閉店した店舗
- 開店・閉店時期
- 街の変遷に関する記録
- 情報の出典と根拠
- 記録者と確認日

史料で確認された事実と、個人の記憶・伝聞を区別する。

過去の情報については、確認できた時期と根拠を記録する。創業年や閉店年を推測で補完しない。

将来、3D都市モデルや年代別の地図を導入する場合も、現在の店舗データと歴史データを分離して管理する。

---

# 12. データ取得・初期データ

## 12.1 初期データの目標

最初は20〜50店舗程度を登録し、アプリの動作と使い勝手を検証する。

これは初期開発用の目安であり、全地域の網羅性を意味しない。

可能であれば、東京都と埼玉県の複数エリアを含める。ただし、未確認の店舗情報を実在データとして登録しない。

## 12.2 データの収集方法

以下の情報源を利用候補とする。

- OpenStreetMap等のオープンデータ
- 店舗の公式ウェブサイト
- 店舗の公式SNS
- 利用条件を満たす公開データ
- 開発者本人による現地確認

各情報源について、利用規約、ライセンス、出典表示義務、保存・再利用条件を確認する。

ウェブサイトの無断スクレイピングや、規約に反する大量取得を実装しない。

## 12.3 データの確認状態

以下の状態を使い分ける。

- 未確認
- 確認済み
- 閉店の可能性あり
- 閉店確認済み

店舗の存在、営業時間、価格、立ち呑み形式は、それぞれ確認状態が異なる場合がある。

将来は項目別の確認状態に拡張できる設計とする。

## 12.4 地図タイルと外部サービス

地図タイル提供元と外部APIの利用条件を確認する。

- 必要な帰属表示を行う
- 利用制限を守る
- APIキーが必要な場合は安全に設定する
- APIキーをソースコードや公開リポジトリに直書きしない
- キーがなくても起動できるよう、未設定時の案内を表示する
- 外部サービスの停止時に、アプリ全体がクラッシュしないようにする

外部APIを利用できない場合は、機能を明確に無効化するか、代替表示を提供する。

# 13. UI・操作性

## 13.1 基本要件

- 表示言語は日本語
- 通貨は日本円
- 日時は日本時間を基本とする
- PCブラウザでの利用を優先
- 文字サイズとコントラストを確保
- 操作ボタンに明確なラベルを付ける
- 読み込み中・エラー・データなしの状態を表示
- 店舗情報の更新日時を分かりやすく表示

## 13.2 データ編集

店舗の追加・編集フォームでは、必須項目と任意項目を明示する。

必須項目は原則として以下とする。

- 店名
- 緯度
- 経度

住所、ジャンル、価格、営業時間、出典は入力できる範囲で登録する。

緯度・経度の入力ミスを検出する。地図上をクリックして位置を選択する方法も提供する。

店舗を削除する場合は確認を求める。訪問記録が存在する場合は、その記録をどう扱うか選択できるようにする。

## 13.3 状態表示

以下の状態に対応する。

- 初回起動
- 店舗データなし
- 検索結果なし
- 地図データ読み込み中
- 外部地図サービスに接続できない
- 店舗データの保存に失敗
- JSONの読み込みに失敗
- バックアップの出力に失敗

エラー発生時は、原因と利用者が取れる対処を日本語で表示する。

---

# 14. セキュリティ・プライバシー

本アプリは個人利用を前提とする。

- 訪問記録や感想を外部サーバーへ送信しない。
- 写真は初期段階ではファイル名・参照先などの管理を基本とし、画像の外部アップロードを自動実行しない。
- 外部サイトを開く場合は、リンク先が分かるようにする。
- インポートするJSONは型・サイズ・値を検証する。
- 任意のHTMLやスクリプトをデータとして実行しない。
- 地図表示用の文字列を安全に描画する。
- APIキーを公開コードに埋め込まない。
- バックアップデータには個人的なメモが含まれる可能性があることを説明する。

ブラウザ内保存データは、ブラウザのデータ削除などで失われる可能性があるため、定期的なバックアップを案内する。

---

# 15. パフォーマンス

- 地図操作が店舗データの全再計算を頻繁に引き起こさないようにする。
- 大量の店舗を想定し、クラスタリングまたは縮尺に応じた集約表示を導入する。
- 地図のレイヤー更新とReactのUI更新を適切に分離する。
- 検索条件の変更で地図全体を再生成しない。
- 初期データが数十件の段階でも、将来数千件へ増やせる構造にする。
- 外部APIへのリクエストを必要以上に繰り返さない。
- エラー時に無限の再試行を行わない。

パフォーマンスの評価は、実際の開発環境で確認し、測定せずに高速性を保証しない。

# 16. テスト・受け入れ条件

以下を満たした時点でv1.0の完成とする。

## 16.1 起動・地図

- Windows上で指定のコマンドから起動できる。
- READMEに記載された手順で再現できる。
- ブラウザに3D地図が表示される。
- 地図を移動・拡大・縮小・回転できる。
- 地図タイルの読み込み失敗時に、原因を把握できるエラーが表示される。

## 16.2 店舗

- 店舗マーカーが登録座標に表示される。
- 店舗を選択すると詳細が表示される。
- 店舗を追加・編集できる。
- 店舗を削除できる。
- 店舗の重複登録を防止できる。
- 検索条件を複数組み合わせられる。
- 未確認の営業時間や価格を確定情報として表示しない。

## 16.3 密度表示

- 店舗密度レイヤーを表示できる。
- 通常表示へ戻せる。
- 凡例を表示できる。
- フィルター条件が密度計算に反映される。
- データがない地域と、調査済みで店舗が少ない地域を区別できる。

## 16.4 個人記録

- 店舗に訪問記録を追加できる。
- 感想と注文内容を保存できる。
- ページを再読み込みしても記録が保持される。
- お気に入りと行きたい店を登録・解除できる。
- 記録をJSONとしてエクスポートできる。
- エクスポートしたデータをインポートして復元できる。

## 16.5 はしご酒

- 複数店舗をルートに追加できる。
- 店舗の順序を変更できる。
- ルートを保存・再読み込みできる。
- 経路情報が未取得の場合に、実際の徒歩ルートを取得済みと誤表示しない。

## 16.6 品質

- TypeScriptの型チェックが通る。
- ビルドが成功する。
- 主要な単体テストが通る。
- JSONの不正データを拒否または安全に処理する。
- ブラウザのコンソールに未処理の重大なエラーがない。
- READMEと実際の実装が一致している。

テストは可能な限り自動化する。外部地図サービスに依存するテストと、ローカルだけで完結するテストを分離する。

# 18. Claude Codeへの作業指示

以下を開発作業全体の指示とする。

1. 作業開始前にリポジトリの構成、既存ファイル、依存関係、起動方法を調査する。
2. 既存実装がある場合は、それを理解してから変更する。
3. 本仕様書を `docs/SPEC.md` に保存する。
4. 実装計画を `docs/DEVELOPMENT.md` に記載する。
5. まずPhase 1を完成させ、その後Phase 2以降を進める。
6. 各フェーズで、実装・型チェック・テスト・起動確認を行う。
7. 実装していない機能を、完成済みとして報告しない。
8. APIキー、外部サービス、データライセンスが必要な場合は、実装前に条件を確認する。
9. 外部サービスの利用条件が不明な場合、勝手に利用を前提とせず、代替案を提示する。
10. 店舗の実在情報や営業時間を捏造しない。
11. 実在情報が未登録の場合は、明示的なデモデータを使う。
12. デモデータには実在店舗と誤認されない識別情報を付ける。
13. 外部サービスが利用できなくても、店舗の追加・編集・個人記録などの主要機能が動作する構造を目指す。
14. 大きな設計変更を行う場合は、変更理由と影響を説明する。
15. 完成時に、起動コマンド、設定方法、データの保存場所、バックアップ方法、既知の制約をREADMEに記載する。

## 最初の作業

まずPhase 1だけを実装する。

Phase 1の完成後、以下を報告する。

- 作成・変更したファイル
- 採用した技術とその理由
- 地図データの提供元
- 起動コマンド
- 実施したテストと結果
- 未解決の問題
- Phase 2に進むために必要な作業

Phase 1が完成していない場合は、Phase 2以降の機能を先に実装して問題を複雑化させない。

# 19. 完成の定義

v1.0の完成とは、単に地図が表示されることではない。

利用者が以下の一連の操作を実行できることを完成条件とする。

1. アプリを起動する。
2. 埼玉県・東京都の地図を3Dで眺める。
3. 店舗を検索して地図上で選ぶ。
4. 価格やジャンルなどの情報を確認する。
5. 訪問した店を記録する。
6. 酒場密度を切り替えて街の違いを眺める。
7. 複数店舗を選んではしご酒の計画を作る。
8. 自分のデータをバックアップする。
9. 次回起動時にも記録が残っていることを確認する。

これらを実現し、さらに店舗や個人記録を増やしても設計を大きく作り直す必要がない状態を目指す。

**最終目標は、店を探すために開いた地図を、気づけば街を探検するためにも開いてしまうアプリにすることである。**
